# Prior art for database authority and Claude reach

> Checked 2026-11-03; recheck by 2027-02-03 for product behavior, maintenance and MCP compatibility. Dates below are the latest default-branch commit observed through the GitHub API on 2026-11-03 unless marked as a release or “not published.” This document records public designs only.

Scope: [database authority](https://github.com/112345brian/knowledge/pull/91) and its [audit](https://github.com/112345brian/knowledge/pull/93) and [export](https://github.com/112345brian/knowledge/pull/95) increments; [skills and MCP reach](https://github.com/112345brian/knowledge/pull/96). The decision to build a custom store is settled. These verdicts concern its pieces. The constraints are one user, personal data with private/normal/off visibility, a Mac with a synced folder and a Windows machine, a public code repo with no personal data, Python 3.11+, uv, a Typer CLI, enforced onion architecture, and Claude Code, Desktop chat and ideally mobile.

## Recommendations and open questions

1. Keep the chosen SQLite design in PRs #91/#93/#95: application-controlled writes, transactional revisions and audit rows, deterministic per-table export with manifests and hashes, and a restore drill. The closest Git-friendly export pattern is sqlite-diffable; Paperless-ngx and calibre support the distinction between a readable export and a verified recovery path. Keep the live writable DB local, outside any sync folder. Stage snapshots outside the sync folder, then publish completed, versioned files and validate their hash plus `PRAGMA integrity_check` after receipt. A local rename is not evidence of an atomic cloud transfer.
2. Decide whether Windows needs **read-only** use or independent writes. A single authoritative writer with snapshot transfer is compatible with the current design. If Windows must write without divergent copies, route operations to the one machine hosting the database; [SQLite's network guidance](https://sqlite.org/useovernet.html) favors client/server access over a shared DB file. Independent local writes require a merge/conflict policy; neither a sync folder, Litestream nor `sqlite3_rsync` supplies it. Dolt, cr-sqlite and sqlite-sync are candidates for a later prototype, not recommendations to migrate now.
3. Keep PR #96's local MCP and skills for Claude Code and Desktop chat. The first report understated the evidence for Desktop chat and for mobile Cowork skills. Ordinary iOS/Android chat skill triggering is still unverified. The basic-memory research skill demonstrates a concrete approval-before-save pattern; keep that rule explicit for knowledge-record. OKF's source, verification and stale-date fields are useful schema references, but its advisory trust signal and passive date field do not implement this repo's recall policy. Server-side mode enforcement remains the privacy boundary.
4. If mobile **chat** needs the store, first decide whether a normal-only snapshot may be hosted for Anthropic's cloud to reach. A future connector should have only named read tools over that snapshot, a read-only DB handle, no private rows and OAuth per the current MCP spec. Test Claude's client behavior, token audience, and end-to-end denial of writes before deployment. No source found guarantees a safe personal-store connector merely by marking a tool read-only.

Unverified: ordinary mobile chat use of uploaded custom skills; the owner's Desktop configuration in practice; receiver-side atomicity for MEGA/Dropbox rename; a two-device Mac/Windows snapshot restore; and Claude's exact support for MCP 2026-07-28 and Client ID Metadata Documents. No claim above depends on those tests succeeding.
