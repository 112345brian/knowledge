# Knowledge

A personal knowledge base built as a local SQLite database from reviewed facts and source records,
with a CLI for ingesting, reviewing, searching, and auditing them.

- **Provenance:** every fact carries a trust level and its sources; claims can be audited against
  the facts they cite.
- **History:** changes are appended as revisions, never overwritten, so any fact has a full history.
- **Privacy:** facts are `normal` or `private`; privacy rules are checked before a fact is stored.
- **Reproducible:** the database is a build artifact. Edit the inputs or the code, then rebuild.

## Data boundary

This repository holds code, schemas, and synthetic test fixtures only. It must not contain real
facts, private configuration, local file paths, or client data. Those live in a separate private
data directory.

- A per-user `config.toml` (outside this repository) defines the database location, the data directory,
  the input paths, and the enabled optional sources.
- It is found at `~/.config/knowledge/config.toml`, or wherever `KNOWLEDGE_CONFIG` points.
- Nothing from it may appear in source files, docs, examples, snapshots, or test goldens. Tests
  build synthetic data in temporary directories.

## Quick start

```sh
uv sync
mkdir -p ~/.config/knowledge
$EDITOR ~/.config/knowledge/config.toml     # see "Configuration" below
uv run python knowledge.py build
uv run python knowledge.py search "example terms"
```

`build --check` builds into a throwaway file and reports counts without touching the live database.

### Configuration

The build reads one TOML file: `$KNOWLEDGE_CONFIG` if set, otherwise `~/.config/knowledge/config.toml`
(`$XDG_CONFIG_HOME` is honored; on Windows the per-user config directory). A named file that does not exist is an
error, never a silent fallback.

```toml
db_dir = "~/MEGA/library/knowledge"            # where the built database goes
data_dir = "~/code/knowledge-private/data"     # where your fact files and rules live
notes_vault = "~/MEGA/notes"                   # optional: a directory of citation notes
health_dir = "~/MEGA/health"                   # optional
client_sources = ["concerts", "ratings"]       # optional: which client sources to build

[client_inputs]                                # the inputs those sources read
concerts_csv = "~/MEGA/concerts.csv"
```

- **Required:** `db_dir` and `data_dir`. **Optional:** `notes_vault`, `health_dir`, `client_sources` and the
  `[client_inputs]` table. Nothing is guessed: a client source is built only if it is listed in `client_sources`
  (the default is the core alone), and one listed without its input stops the build with a configuration error.
- Unknown keys are an error, so a typo is reported instead of ignored.
- Any setting can be overridden by an environment variable: `KNOWLEDGE_DB_DIR`, `KNOWLEDGE_DATA_DIR`,
  `KNOWLEDGE_NOTES_VAULT`, `KNOWLEDGE_HEALTH_DIR`, `KNOWLEDGE_CLIENT_SOURCES` (a JSON list).
- A step that needs an optional setting you left out stops with a message naming it. `paths.py` and
  `locations.py` document the full set.

#### Several machines, and chezmoi

Every path may start with `~`, which each machine resolves for itself, so most files need no per-machine edits.
For the differences that remain there are two ways to keep one synced config:

- **A local override file.** `config.local.toml` beside `config.toml` is merged over it, key by key (a
  `[client_inputs]` table is merged too). Keep it out of what you sync; it holds only what differs on this machine.
- **chezmoi templates.** The default path is the same on macOS and Linux, so one source file serves both:

  ```
  ~/.local/share/chezmoi/dot_config/knowledge/config.toml.tmpl
  ```

  ```toml
  db_dir = "~/MEGA/library/knowledge"
  data_dir = "~/code/knowledge-private/data"
  {{- if eq .chezmoi.hostname "desktop" }}
  notes_vault = "D:/Notes"
  {{- else }}
  notes_vault = "~/MEGA/notes"
  {{- end }}
  ```

  Use `private_dot_config/...` if you want chezmoi to create the file with mode 0600. Do not `chezmoi add`
  `config.local.toml`.

#### Paths on Windows, macOS and Linux

The config may write `~/...`. The database stores that text as written, so it never carries one machine's
home directory; only reads expand it. `~` means the OS user's home unless `KNOWLEDGE_HOME` is set, which
redirects it, e.g. `KNOWLEDGE_HOME=E:\` makes `~/MEGA/vault` read from `E:\MEGA\vault`. Set it in the
environment of whatever runs the build; nothing about it is written to the database or to the config file.
Absolute paths in the config are not affected.

All files the project reads and writes are UTF-8 with LF line endings on every OS, and paths handed
between layers are joined by `locations.join_path`, which keeps the separator the directory already uses.

### Review inbox

`knowledge.py inbox` serves the pending-fact review page on `127.0.0.1`. It displays private facts,
so keep it local: do not put it behind a proxy, tunnel, or port forward.

## How the build works

`build.py` applies `schema.sql` and runs the ordered steps in `build_rules.py`. The core pipeline
builds without any optional source. A checkout enables optional sources (under `client/`) through
its config file; each may add schema fragments and ingest steps. No base module (the repo root
or `ingest/`) imports from `client/`: a client source owns its ports, records and adapters, and an
import-linter contract and `tests/test_client_boundary.py` fail the build if the direction is broken.

The built database and its normal-view copy are generated. Never edit either by hand.

### Adding a client source

A client source lives under `client/`. Register it in `client/bootstrap.py`; the base loads that file by path and
calls `register(registry)`. Adding its code needs no edit to base code or repository configuration. Add its name
to `client_sources` in the config file to enable it. The source's `Input` declarations read settings
from `Locations.client_inputs` by setting name.

For example, add a step and schema for a small feed:

```python
# client/bootstrap.py
from client_registry import ClientSource, Input, Step

def register(registry):
    registry.add(ClientSource(
        "my_feed",
        steps=(Step("client/my_feed.py", after="ingest/facts.py"),),
        schema=("client/my_feed.sql",),
        inputs=(Input("MY_FEED_JSON", "my-feed-json", required=True),),
        report_tables=("my_feed_rows",),
    ))
```

```python
# client/my_feed.py
def run(con, ctx):
    path = ctx.locations.client_input("MY_FEED_JSON")
    # Read and load the feed using the client's adapters.
```

Then add `client_sources = ["my_feed"]` and, under `[client_inputs]`, `my_feed_json = "/path/to/my-feed.json"` to the
config file. A required setting omitted from it makes the build stop with a configuration error.

`ClientSource` can also declare ordered steps with `Step(after=..., order=...)`, shared schema fragments, `Tool`
commands, synthetic `leak_rows`, private `data_files`, report tables, and fact metadata that contributes to the
personal-topic heuristic.
The base guarantees that adding a source does not require editing files outside `client/`. The architecture test
derives ring rules from module suffixes; `client/` is not governed by `tach.toml`.

Procedures for registering facts are in [docs/register-facts-protocol.md](docs/register-facts-protocol.md).

## Project layout

| Path | Contents |
| --- | --- |
| `knowledge.py`, `cli_*.py` | Typer CLI (driving adapter) |
| `build.py`, `build_rules.py`, `ingest/` | Build pipeline and core ingest steps |
| `client/` | Optional sources, enabled per checkout |
| `*_service.py` | Application services that orchestrate rules through ports |
| `*_rules.py`, `*_port.py` | Pure domain rules and port protocols |
| `*_store.py`, `paths.py`, `clock.py` | Adapters for the database, files, git, and time |
| `schema.sql` | Core database schema |
| `docs/` | [Index](docs/README.md): [architecture](docs/architecture.md), [competency questions](docs/competency-questions.md), [fact registration protocol](docs/register-facts-protocol.md) |
| `tests/` | Test suite and synthetic fixtures |

The code follows an onion architecture: dependencies point inward, domain rules do no I/O, and
services reach files, the database, and processes only through ports. [docs/architecture.md](docs/architecture.md)
has the module map and the enforced boundaries.
