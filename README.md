# knowledge

This repo (`~/programming/knowledge`) is the pipeline: `schema.sql` + the
numbered ingest/seed scripts + the CLI. It contains **no personal data and
no personal file paths** — those live in a private companion repo,
`knowledge-private`, expected checked out as a sibling directory
(`../knowledge-private` relative to this one):

- `knowledge-private/local_paths.py` — every real external path (the health
  vault, the concerts export, the RYM export, the scrobbles export, and
  where `knowledge.db` itself lives). This repo's own `paths.py` is a thin
  loader that imports from there; it carries zero personal path strings.
- `knowledge-private/data/` — the actual fact/source content: hand-authored
  sources (`manual_sources.json`), interpretive facts (`pilot_facts.json`,
  `facts_batch1-4.json`), and ad hoc facts (`general_facts.json`, appended
  to via `add_fact.py`).

Without `knowledge-private` checked out alongside it, this repo won't run —
that's intentional, not a bug: it's meant to show the pipeline design, not
to be runnable standalone by anyone who clones it.

`knowledge.db` itself lives at the path `local_paths.py` designates
(currently inside the MEGA-synced folder, deliberately outside *both* git
repos, so a sync client never touches either repo's `.git` internals, but
the built artifact still ends up synced). `python3 knowledge.py build`
writes a timestamped backup there before every rebuild as a safety net,
since git isn't tracking the db file's history (it isn't in either repo).

`knowledge.db` is a **build artifact** of the scripts here plus the data
files in `knowledge-private`. Never hand-edit the `.db` file with ad hoc
`ALTER`/`INSERT` statements — change a script and rebuild.

## CLI

`knowledge.py` is the one entry point, a [Typer](https://typer.tiangolo.com) app (`--help` on it and on every command; shell completion via `--install-completion`). `build.py`, `add_fact.py` and `clean_concerts_csv.py` still run standalone with plain `python3` and do not need typer.

**Setup (once):** the CLI and the tests need typer and pytest, declared in `pyproject.toml` and installed into a repo-local `.venv` (git-ignored) by [uv](https://docs.astral.sh/uv/). Nothing goes into the system python.

```bash
uv sync                                        # creates .venv with typer + pytest
export KNOWLEDGE_PRIVATE_DIR=~/programming/knowledge-private   # as before
uv run pytest                                  # run the tests (plain `python3 -m pytest` fails: no typer)
uv run python knowledge.py --help
```

```bash
uv run python knowledge.py build            # rebuilds knowledge.db in place (auto-backs up the old file first)
uv run python knowledge.py build --check    # builds into a throwaway temp file and reports counts; live DB untouched
uv run python knowledge.py add-fact "statement" --subject some-subject --trust medium   # forwards every argument to add_fact.py; see add_fact.py --help
uv run python knowledge.py add-facts FILE|- [--status active|pending] [--captured-via X] [--session-id S] [--dry-run] [--allow-dirty] [--json]   # batch of reviewed facts from a JSON list (file or stdin); see the add-facts bullet below
uv run python knowledge.py clean-concerts   # dedupes the concerts export in place
uv run python knowledge.py search "terms" [--subject x] [--trust high] [--personal-only|--not-personal] [--status S] [--include-pending] [--limit N] [--json]   # active facts only by default
uv run python knowledge.py show <fact_id> [--as-of DATE] [--json]     # also prints visibility, source key and provenance (captured via/session/at, source quote) when set
uv run python knowledge.py history <fact_id|source_key> [--json]       # every revision, oldest first, with what changed
uv run python knowledge.py audit-claims [--json]                       # claims resting on superseded/retracted/past-recheck facts; exit 1 if any
uv run python knowledge.py audit-sources [--json]                      # facts whose source file changed / went missing / moved since extraction (SHA-256 baseline); exit 1 if any
uv run python knowledge.py supersede <fact_id|source_key> --by <fact_id|source_key> --reason "..." [--allow-dirty] [--json]
uv run python knowledge.py retract <fact_id|source_key> --reason "..." [--allow-dirty] [--json]
uv run python knowledge.py set-visibility <fact_id|source_key> normal|private --reason "..." [--allow-dirty] [--json]
uv run python knowledge.py privacy check "statement" --subject s [--requested normal|private] [--json]
uv run python knowledge.py privacy rules [--json]
uv run python knowledge.py privacy tag|untag <subject> [--tag private|normal] [--allow-dirty] [--dry-run]
uv run python knowledge.py privacy add-keyword|remove-keyword "<word or name>" [--allow-dirty] [--dry-run]
uv run python knowledge.py subjects [--include-pending] [--json]   # counts active facts (plus pending with the flag)
uv run python knowledge.py facts [--subject x] [--trust high] [--status active|pending|superseded|retracted] [--include-pending] [--personal-only|--not-personal] [--limit N] [--json]   # active only by default; --status X shows only X and overrides --include-pending
uv run python knowledge.py review-pending [--json]                     # the pending queue, oldest first
uv run python knowledge.py approve REF... | --all [--reason TEXT] [--allow-dirty] [--json]   # REF = fact id or source_key
uv run python knowledge.py reject REF... --reason TEXT [--allow-dirty] [--json]
uv run python knowledge.py migrate-memory [--memory-root DIR] [--dry-run] [--json] [--allow-dirty] [--verbose]   # Claude Code memory -> private pending facts (see below)
uv run python knowledge.py edit <fact_id|source_key> [--statement T] [--trust L] [--trust-rationale T] [--recheck-by YYYY-MM-DD] [--notes T] --reason R [--allow-dirty] [--json]   # appends a revision; "" clears rationale/recheck-by/notes
uv run python knowledge.py inbox [--port N] [--no-open]                # local review page for pending facts (127.0.0.1 only; see "Inbox")
```

`--json` on a read command prints the same rows the library function returns (`search_facts`, `get_fact`, `list_subjects`, `list_facts`, `revisions.get_history`, `revisions.get_fact_as_of`; `audit-claims --json` prints `{"stale_premises": [...], "unparseable_rechecks": [...]}`). An invalid full-text query (unbalanced quote, empty string) prints `error: search failed: ...` and exits 1.

**`migrate-memory` (#29)** imports Claude Code memory (`<root>/*/memory/*.md`, root default `~/.claude/projects`; `MEMORY.md` indexes, symlinks and `feedback` files are skipped and listed/counted) as private, pending facts through `add_fact.append_fact`, then makes one commit of `general_facts.json` in knowledge-private. Always run `--dry-run` first. Rules (also in `migrate_memory.py`'s docstring): `project`/`user`/`reference` files become one fact each, subject `claude-memory-<type>`, trust `unverified`, `captured_via=migrate-memory`, `session_id` from `originSessionId`; `recheck_by` = `modified` date + 180 days (today + 180 when `modified` is missing or unparseable, with a warning); statement = the body with whitespace collapsed, cut at 600 chars with the full text kept in `notes` (files over 64 KiB are refused, never truncated). `source_key` = `mm-` + a hash of `<project folder>/<file name>`, so a second run adds nothing, and a file edited after migration is reported as "changed since migration" and not re-added. Files with no/odd frontmatter, an unrecognized type, bad encoding or no content are reported as problems (exit 1) while the rest is processed. Exit 3 means the facts are written but the commit failed. If a run is killed before its commit the tree is dirty: rerun with `--allow-dirty`.

**CLI first (parity rule).** Everything doable from a UI button, the inbox or an MCP tool is also a CLI command. For every new action, in this order: (1) a library function in `knowledge.py` (or its own module): pure, importable, returns data, never prints or exits; (2) a Typer command that only parses flags and prints, with `--json` if it reads; (3) the MCP tool / inbox handler, which calls the same library function. Register the action in `cli_parity.py` (`ACTIONS`: action name -> CLI command path). `mcp_server.py` and `inbox.py` must declare `PARITY_ACTIONS` (the action names they expose); `tests/test_cli_parity.py` fails if a registered action has no real command, or if either module exposes a name with no registry entry.

## Pipeline order

1. `schema.sql` — canonical DDL: every table, index, view, FTS5 virtual table + triggers.
2. `01_seed_sources.py` — loads `knowledge-private/data/manual_sources.json`: hand-authored sources (DEXA scans, bloodwork panels, a few literature pilots, small manual instruments) that don't come from parsing vault frontmatter or a vault db.
3. `02_ingest_literature_sources.py` — mechanically parses the vault's `sources/*.md` frontmatter files into `sources` rows.
4. `03_ingest_measurements.py` — pulls every structured numeric reading from the vault's own db: DEXA, bloodwork, tape, strength checkpoints, then daily/weekly summaries and the full raw logs (per-set training, per-meal/per-food nutrition, Fitbit, micronutrients). Creates its own `vault-db-*` sources for the raw tables it reads.
5. `04_ingest_facts.py` — loads `knowledge-private/data/pilot_facts.json` (hand-authored facts) and `facts_batch1-4.json` (facts extracted by background agents reading the vault's synthesis and harm-reduction notes) into `facts`/`fact_sources`/`fact_measurements`. Classifies `is_personal` with a documented heuristic and resolves `origin_path` from each fact's `notes` field.
6. `05_seed_claims.py` — hand-authored broader claims and which facts back them.
7. `06_seed_subject_hierarchy.py` — arranges `aas-*` subjects under `anabolic-steroids` and `training-*` subjects under a new `training` umbrella.
8. `11_seed_general_facts.py` — loads `knowledge-private/data/general_facts.json`: ad hoc facts with no project or vault behind them, added one at a time via `add_fact.py` rather than in a batch. Defaults new subjects to `domain='general'` instead of `health-and-fitness`.
9. `12_apply_fact_revisions.py` — reads `knowledge-private/data/fact_revisions.jsonl` (the revision log, see below), validates it and writes `fact_revisions` plus each fact's current state into `facts`. Runs last among the fact steps; a missing or empty log is fine.

## Inbox (#33)

`knowledge.py inbox` serves a review page for `pending` facts (statement, subject, visibility and the privacy rule behind it, provenance, source quote, date added, a pending count) with Approve, Edit, Reject, Make private and "Approve all N shown". No JavaScript: every button is a plain form. Standard library only (`inbox.py` is the server and page, `cli_inbox.py` the two Typer commands `inbox` and `edit`; the write logic is in `lifecycle`/`review`, see Architecture enforcement).

- **Local only.** It binds `127.0.0.1` (there is no `--host`) and shows private facts, so never put it behind a proxy, tunnel or port forward, and never run it in the remote normal-tier process (#26). It refuses non-loopback peers (403) and any `Host` header other than `127.0.0.1:PORT` / `localhost:PORT` (421, DNS rebinding). Mutations are POST-only to `/action`, need the per-run random token that is embedded in the page (403 otherwise), a form content type, and, if sent, a same-origin `Origin`. No CORS headers; a CSP forbids scripts; every field is HTML-escaped.
- **Snapshot.** The list comes from the built db, so rebuild (`knowledge.py build`) to see new pending facts. Each fact's current state is read from the data files and revision log, so a fact approved, rejected or edited since the rebuild is shown as it is now (or hidden, with a count).
- **Every action is a library call, appending a revision.** Approve/Reject: `review.approve` / `review.reject`; Edit: `lifecycle.edit_fact` (= `knowledge.py edit`; statement, trust level and rationale, recheck-by, notes; the subject is immutable and an edit whose statement trips a privacy rule also raises visibility); Make private: `lifecycle.set_visibility` with `raise_only=True` (raise-only: a request for `normal` is refused, naming the privacy rule when one floors the fact). Each is one locked append and one commit in the private repo, refused up front on a dirty tree. A fact reviewed elsewhere since the page loaded gives a clean "already approved/rejected" message, never a second write.
- **Bulk approve** approves exactly the facts shown (like `approve KEY...`), not `approve --all`: `--all` would also approve facts added after the last rebuild that nobody has seen.
- Parity (#34): `inbox.PARITY_ACTIONS` maps each button to its CLI command (`review-pending`, `approve`, `reject`, `edit`, `set-visibility`). `cli_parity.PENDING_COMMANDS` holds the entries whose command is built by another change; `tests/test_inbox.py` skips only those entries until the command exists.

## Fact revisions (#30)

A fact entry is never edited. The JSON entry is **revision 1**; every later change appends one line to `knowledge-private/data/fact_revisions.jsonl` (`{source_key, revision, changed_at, changed_via, session_id, change_reason}` plus a full snapshot of `statement, trust_level, trust_rationale, status (pending|active|superseded|retracted), visibility, superseded_by (a source_key), recheck_by, recheck_rationale, freshness, notes`, in that fixed key order). `facts` is still a real table holding the *current* state (the latest revision); `fact_revisions` holds every revision including the implicit revision 1 (`changed_at` comes from the entry's `date_added`, `changed_via` `original`).

- **`source_key`**: the stable identity a revision points at. `add_fact.py` gives every new fact one (`f-<12 hex>`). Entries that predate it get a deterministic `legacy-<10 hex>` key derived from file name + subject + statement (`revisions.derive_keys`; later duplicates of identical content get `-2`, `-3`). The build derives these in memory when an entry has none, so it works before the backfill; `backfill_source_keys.py` writes the *same* keys into the files, so building before or after yields identical rows. Revisions may be appended before or after the backfill.
- **Backfill (one-time, in-place edit of the legacy JSON files)**: `python3 backfill_source_keys.py` is a dry run; `--apply` writes. It inserts `"source_key"` as the first key of each entry that lacks one and changes nothing else (every other byte is preserved and the result is verified), under the same lock and atomic replace as `add_fact.py`; running it again changes nothing. Use `--data-dir` to try it on a copy. Commit the result in `knowledge-private` afterward.
- **Library API (`revisions.py`)**: `append_revision(source_key, changes, reason, via, session_id=None)` returns a `RevisionResult(ok, errors, revision)` (it refuses instead of raising, so check `ok`; a test fails if any caller discards the result); `get_history(db, fact_id | source_key)` lists every revision in order; `get_fact_as_of(db, fact_id | source_key, "YYYY-MM-DD")` returns the revision in force at the end of that day (UTC), or the exact moment for a full timestamp, `None` if the fact did not exist yet. `db` is a connection or a path. CLI: `knowledge.py history <id|source_key>` and `knowledge.py show <id> --as-of DATE` (`DATE` is `YYYY-MM-DD`, meaning the end of that day UTC, or an ISO timestamp; a bad date, an unknown fact, or a date before the fact existed is a one-line error, exit 1). An all-digit argument to `history` is always a fact id.
- **Validation at build time** (fails the build naming `fact_revisions.jsonl:<line>`): revision numbers contiguous per fact starting at 2 (a gap or duplicate fails), `changed_at` not before the previous revision, every `source_key` exists, `superseded_by` resolves, every line well-formed. `append_revision` runs the same checks first, so it will not write a line the build would reject. Blank lines are ignored. Hand-editing an old line is caught only by these checks and by git.
- `facts.status` now also allows `pending` (revisions and entries may set it; the review workflow is #6, see "Pending review" below).

## Modes: off | normal | private (#22)

`modes.py` is the query layer every tool must read facts through (the MCP server #2 and the CLI `--mode` option are thin callers; the CLI option is not wired yet). A `modes.Session` holds the mode for one conversation (a fresh one is `normal`; sessions never share state). `set_mode(session, mode)` is a user action ("database private") and must not be a tool the model calls on its own.

- **off**: every read and write raises `ModeOff`. **normal**: only facts stored `visibility='normal'`, on a subject not tagged private, and only `active` (plus `pending` with `include_pending=True`). **private**: everything.
- Reads: `search_facts`, `get_fact` (id or source_key), `list_facts`, `list_subjects`, `get_history`, `get_fact_as_of`, each `fn(session, con, ...)` with the same row shapes as `knowledge.py` / `revisions.py`. The filter is in the SQL (join on `facts.visibility`), so it cannot be skipped. A hidden fact answers exactly like a missing one (`None` / `[]`), subject lists and counts only count visible facts, and in normal mode revision snapshots stored private are left out (a fact currently private has no history at all). Claims, measurements and other tables are not exposed. Bad search text (empty, unbalanced quote) raises `InvalidQuery`.
- Writes: `prepare_write(session, subject, statement, rules, requested=None)` resolves through `privacy.resolve_visibility` and gates it; `check_write(session, resolution)` gates an existing `privacy.Resolution`. Store the returned `.visibility`. The model's requested value is only a resolver input; with none given, private mode uses `private`, never `normal`. Normal mode refuses a resolved-private write and tells the user to say "database private" first.
- Attach `modes.with_mode(session, result)` to every tool response so the current mode is always visible.
- `tests/test_modes.py` fails if any module outside the query layers and build pipeline reads `facts` / `fact_revisions` / `facts_fts`, or if a caller discards a `check_write` / `prepare_write` result.

## Adding new data

- **New literature citation**: drop a note in the vault's `sources/` folder with the usual frontmatter, then rebuild — `02_ingest_literature_sources.py` picks it up automatically.
- **New DEXA scan / lab panel / logged data**: update the vault's own db (its own pipeline handles that), then rebuild — `03_ingest_measurements.py` re-reads it. Note this makes `measurements` a snapshot as of the last rebuild, not a live view; rerun `build.py` after new vault data lands if you want it reflected here.
- **New interpretive fact from reading more of the vault**: this step still needs a human/agent to actually read the source file and produce a JSON object matching the shape used in `facts_batch*.json` (see `04_ingest_facts.py` for the exact fields), added to `knowledge-private/data/`. Extraction prompts used for the existing batches are preserved in this session's transcript / the `project_knowledge_db` memory note, not in either repo.
- **New original claim/decision with no vault file behind it**: add it to `knowledge-private/data/pilot_facts.json` (or a new manually-curated JSON file there) with an explicit `origin_path` (or `null` if it's genuinely un-sourced), then rebuild.
- **A stray, not-project-specific fact** (nothing to do with bodybuilding or any other vault — just something worth recording): `python3 add_fact.py "statement" --subject some-subject --trust medium --recheck-by 2027-01-01` appends a validated entry to `knowledge-private/data/general_facts.json` (see `add_fact.py --help` for the full flag set: notes, recheck-by/rationale, an existing source citekey, marking it not-personal, etc.), then rebuild. Don't hand-edit that JSON directly — the CLI enforces the shape `11_seed_general_facts.py` expects.
- **Competency questions (#49, `docs/competency-questions.md`, `tests/test_competency.py`)**: the questions the database must be able to answer, each with the command or SQL that answers it today. `tests/test_competency.py` runs every answerable one against a fixture db built from the real `schema.sql` and asserts the shape of the answer, so a schema change that breaks a question fails a test; meta tests keep the document and the tests in step (every answerable question names an existing test, every other one names an issue or says it is proposed). **The list is a draft written by an agent; it is not authoritative until you review it and sign off on issue #49.** Three questions are marked "cannot answer yet" (contradicting facts, a remote client's retrieval with premise warnings, per-kind freshness policy); two of them have no issue yet.
- **Source identifiers (#48, `identifiers.py`, `cli_sources.py`)**: table `source_identifiers(source_id, scheme, value)` with `scheme` one of `doi`, `isbn`, `issn`, `pmid`, `arxiv`, `other`, UNIQUE on (scheme, value). Values are normalized and verified, never fixed by guessing: DOIs are lowercased with `https://doi.org/`, `dx.doi.org` and `doi:` prefixes and trailing punctuation removed; ISBNs lose hyphens, have their check digit verified, and are stored as ISBN-13 (so an ISBN-10 and the ISBN-13 of the same book are one identifier); ISSN is `NNNN-NNNN` with a verified check digit; PMIDs are digits without leading zeros; arXiv ids lose `arXiv:`, URL and version; a PMC id is an `other` value `pmcid:PMC123456`. A bad checksum or a malformed value fails the build naming the note and the offending value. **What the data really carries** (read-only survey of the vault before this was written): `doi` 184 notes, `pmid` 165, `pmcid` 38, `isbn` 1; no `issn` or `arxiv` fields and none in `manual_sources.json`, so only those fields are mapped (the loaders still accept `issn`/`arxiv` and an `identifiers: {scheme: value}` mapping in manual sources). One note had `doi: n/a`; a small documented set of placeholders (`n/a`, `none`, `unknown`, `tbd`, `-`, `?`, ...) means "no identifier" and is skipped, every other malformed value is an error. The real build loads 384 identifiers and found no duplicates. **Duplicates:** two sources sharing an identifier are reported at build time with both citekeys and are NOT merged and NOT silently dropped: the first keeps the row, the other claim is kept in `source_identifier_conflicts` (with the owner) and shown by `source ids`. **CLI:** `knowledge.py source ids CITEKEY [--json]`; `search` and `facts` take `--identifier VALUE` (any spelling: a DOI URL, a hyphenated ISBN, `PMID 123`, `PMC123`; an optional `doi:`/`isbn:` prefix restricts the scheme) and return facts that cite a source with that identifier; `modes.search_facts/list_facts(identifier=...)` do the same behind the visibility gate. **Normal-only DB:** the identifiers of included sources come along (an `other` value containing a listed keyword is dropped); conflicts do not. No network, no resolving, no merging. This bumped `PRAGMA user_version` to 2.
- **Build info and the inputs manifest (#47, `build_info.py`)**: every build records which code and inputs produced it, inside the db. `build_info` has one row: `built_at`, `schema_version`, `code_commit` / `code_dirty` (this repo), `private_commit` / `private_dirty` (knowledge-private), `python_version`, `sqlite_version`. `build_inputs` has one row per input by a **stable key, never a path**: `state` (`present` | `missing`), `sha256`, `size_bytes`, `file_mtime`, `read_at`. Keys: `input:vault-db`, `input:concerts-csv`, `input:rym-export-csv`, `input:scrobbles-json`, `input:data/<name>` for each private JSON file the build can read (manual_sources, pilot_facts, facts_batch1-4, general_facts, fact_revisions.jsonl, privacy_rules, entities, subjects, measurements_snapshot) and `input:vault-source-notes`, an aggregate over the per-note hashes step 02 already stored (so the 435 notes are not re-read). A missing optional input is recorded as `missing`, not an error. Everything except `read_at` is deterministic, so two builds over identical inputs give identical rows. Git state comes from `private_git.describe_repo` (the one module that runs git); a repo with uncommitted changes has `*_dirty = 1`, which is normal while developing. Measured on the real inputs: hashing a 67 MB file takes 0.06 s, so the 122 MB scrobbles export adds about a tenth of a second to a ~19 s build. **Schema version rule:** the single constant is `PRAGMA user_version = N;` in `schema.sql`. Bump it whenever a table, column, constraint, view or trigger changes (comments and whitespace do not count); `tests/test_build_info.py` pins a fingerprint of the schema and fails with the exact new constants to set when you forget. `knowledge.py build-info [--json]` prints the latest build row and manifest; `build-info --compare OTHER.db` lists inputs whose hash differs (`changed`, `now-missing`, `now-present`, `added`, `removed`) and exits 1 when any do. **Normal-only DB:** only `built_at` and `schema_version`; commits, dirty flags, versions and input keys stay out, and the leak test has markers for a commit hash and an input key. Not built: byte-identical reproducible builds, signing, storing the inputs.
- **Custodial history (#46, `acquisition.py`)**: `sources` and `vault_files` gain `acquired_at`, `acquired_via` (`download` | `manual` | `export` | `unknown`), `where_from` (a URL) and `acquired_note`. **Data first:** a source's values come from its frontmatter (`acquired-at`, `acquired-via`, `where-from`, `acquired-note`; step 02) or `manual_sources.json` (`acquired_at`, `acquired_via`, `where_from`, `acquired_note`; step 01). The macOS file attributes only **fill gaps, field by field, and never overwrite** a value the data has: `com.apple.metadata:kMDItemWhereFroms` (the download URL, the first entry of its plist) fills `where_from`, and `com.apple.quarantine` (the download time, UTC) fills `acquired_at`. A value that came from the attributes is marked: `acquired_note` says "from macOS file attributes: where_from, acquired_at" (appended after any note the data has) and `acquired_via` becomes `download` unless the data set it. `vault_files` rows have no data record, so they get the attributes only. A source with neither keeps NULLs; nothing is invented, and a bad value in the data (`acquired-via: scanned`, a non-ISO date) fails the build naming the note. **Read-only and best effort:** it runs `xattr` (list, `-p` for the quarantine value, `-px` for the binary plist, argv lists, no shell, 5 s timeout) and `plistlib`, no new dependency, and only on macOS. Another platform, no `xattr`, a missing, unreadable or attribute-less file, an unparseable plist or a timeout is a silent no-op. It never writes or deletes an attribute (a test pins the argv shapes and scans the source). This is the third documented `subprocess` exception in the import-linter contract, after `private_git` and `knowledge`. **Privacy:** a download URL can reveal private interests, so none of these columns reach the normal-only DB, and the leak test has a `where_from` marker. A build on the real vault was compared before and after this change: every pre-existing column is identical (only the `datetime('now')` build stamps differ). Not built: writing attributes, Spotlight tags, Windows alternate data streams, tracking later moves of a file.
- **Claim argument structure (#44)**: Toulmin's model on `claims` and `claim_facts`. `claims.warrant` (why the cited grounds support the claim) and `claims.qualifier` (how far it holds, e.g. "usually", "in adults") are optional text, blank stored as NULL; `claim_facts.role` is `grounds` (the default, which is what every existing row is), `backing` (supports the warrant) or `rebuttal` (counter-evidence), and `claim_facts.note` says why the fact is linked. One role per (claim, fact); the same fact can be grounds for one claim and a rebuttal of another. `05_seed_claims.py` takes `warrant` and `qualifier` per claim and lets a `fact_match_prefixes` entry be a plain prefix (grounds, as before) or `{"prefix": ..., "role": ..., "note": ...}`; an unknown role fails the build and the two existing claims are not backfilled beyond the defaults. **Audit:** `claims_audit.audit_claims` rows gain `role`, `severity` and `link_note`. A stale `grounds` or `backing` fact weakens the claim: same reasons as before (`superseded`, `retracted`, `past_recheck_by`), severity `weakens`. - **Valid time (#40, `validtime.py`)**: `facts.valid_from` / `valid_to` (also on `fact_revisions`) say when a fact was TRUE, as opposed to `date_added` and the revision log, which say when the db learned or changed it (transaction time). Values are ISO dates at three precisions: `YYYY`, `YYYY-MM`, `YYYY-MM-DD`. A partial date names the whole span: `valid_from 2024` starts 2024-01-01, `valid_to 2024-03` ends 2024-03-31; NULL `valid_from` means no known start, NULL `valid_to` means still true as far as known, and a point in time sets both to the same value (`2024-03-15`, or `2024-03` for all of March). `valid_to` must not be before `valid_from` (compared at the shorter precision, so `2024-03-15` .. `2024-03` is fine and `2024-05` .. `2024-03` is not). The schema CHECKs enforce the shape and the order; `validtime.py` also rejects dates that do not exist (Feb 30, month 13) in `add_fact`, `add_facts`, the ingest and the revision log. They are mutable revision fields (#30): `revisions.append_revision(key, {"valid_to": "2024-06"}, "corrected", "cli")` appends a revision, so `show ID --as-of DATE` answers "what did I believe on DATE about when it was true". `add-fact --valid-from/--valid-to` and `add_facts` items (`"valid_from"`, `"valid_to"`) set them; nothing is inferred from text or from a linked measurement's date. **Read side:** `search`, `facts` and `show` take `--valid-at YYYY-MM-DD` (a full real date; `2024` or `2024-02-30` is an error), and `modes.search_facts` / `modes.list_facts` take `valid_at=` with their visibility gate unchanged. A fact with no interval is always in range. `show --valid-at` prints `Valid: FROM .. TO` and `Valid on DATE: yes|NO` and exits 1 on NO (with `--json` it adds `"valid_at": {"date": ..., "valid": ...}`); it combines with `--as-of` (checked against that revision's interval). `--valid-at` (valid time) is not `--as-of` (transaction time). **A past `valid_to` does not change `status`** (validity is not retraction) and `audit-claims` treats it as information only: a claim resting on a fact that stopped being true is not flagged as stale by that alone. Revision-log format change, same as #39: records need `valid_from` and `valid_to` keys (none existed in knowledge-private when this landed).

- **Freshness (#7)**: every fact has a NOT NULL `facts.freshness`, and the rule is: **every fact needs either a `recheck_by`, or an explicit 'does not decay' assertion with a written `recheck_rationale`; legacy facts that were never reviewed are marked `unreviewed`.** Three values: `recheck` (requires `recheck_by`; blank counts as missing), `no-decay` (requires a non-blank `recheck_rationale` saying why the fact does not decay; `recheck_by` may be empty) and `unreviewed` (legacy only, exempt). Staleness only: a fact that was wrong when typed is `trust_level`'s job. **`no-decay` is not an excuse to default `trust_level` to `verified`**: such a fact still needs an honestly considered trust level reflecting how it was captured. What is enforced: the schema CHECKs only that the required field is present; it cannot judge whether a fact really does not decay or whether a `recheck_by` is sensible. `add_fact.py` needs `--recheck-by DATE|phrase` or `--no-decay --recheck-rationale "why it does not decay"` (neither, or both, is refused; the same at the library level: `NewFact.no_decay`, with freshness derived and never passed in, so a caller cannot supply `unreviewed`); `facts_batch` items carry `recheck_by` or `no_decay: true` plus `recheck_rationale`; `migrate-memory` writes `recheck` (it always computes a `recheck_by`, modified + 180 days). `freshness` is one of the mutable revision fields: a revision may move a fact from `unreviewed` to `recheck`/`no-decay` (that is how legacy facts get reviewed) and between `recheck` and `no-decay`, but `revisions.append_revision` and the build refuse a snapshot the CHECKs would reject (clearing `recheck_by` on a `recheck` fact, `no-decay` with a blank rationale) and `unreviewed` can never be chosen by a revision. `normal_db` copies `facts.freshness` (staleness metadata like `recheck_by`, not private). Legacy entries (`pilot_facts.json` / `facts_batch1-4.json`, no `captured_via`, no `freshness`) ingest as `recheck` if they have a `recheck_by`, otherwise as `unreviewed` plus a 'predates this field / not individually reviewed' note in `facts.notes` and revision 1 (183 of the 295; the JSON files are not edited). - **Pending review (#6, library part)**: a fact added through `add_fact` (`NewFact.status`, default `pending`; only `pending` or `active` are accepted for a new fact) is written with an explicit `"status": "pending"`. A caller that already showed the fact to the user (the `register facts` flow, #32) passes `status='active'`. The 295 legacy entries have no `status` key and stay `active`. `review.list_pending(db)` lists the queue oldest first; `review.approve(refs, reason=..., via=..., data_dir=..., commit=True, allow_dirty=False, db=None)` appends a `status: active` revision (the entry itself is never edited, so history reads revision 1 pending, revision 2 active, and a rebuild shows it active); `review.reject(refs, reason)` appends `retracted` (reason required). `refs` are fact ids (need `db`), source_keys or `"all"`. Only pending facts change: anything else is `skipped` with its current status, so approving twice is a no-op, and the pending check is repeated under the revision log lock so a fact retracted by another process mid-batch is never re-activated. Items are independent (a failing or unknown one is reported and the rest proceed; the append-only log is not rolled back), with one clean-tree check up front and one commit of `fact_revisions.jsonl` for the batch, same git rules as `add_fact`; nothing to approve means no tree check and no commit. **CLI (#6)**: `review-pending [--json]` lists the queue; `approve REF... | --all [--reason TEXT] [--allow-dirty] [--json]` and `reject REF... --reason TEXT [--allow-dirty] [--json]` wrap `review.approve` / `review.reject` (numeric ids resolve through the live db; without a db only source_keys work). Output is one line per item (`approved 6 (source-key)`, `skipped 9: status is 'active', not pending`, `unknown x: ...`), then `Committed <hash>`; with `--json` stdout is one object `{ok, items[{ref, outcome, source_key, reason, revision}], errors, notes, commit, commit_error, detached}`. Exit codes: 0 when nothing went wrong (skipped items are fine, as is "nothing pending"), 1 for a batch error (dirty tree, blank reason) or any unknown/error item (the other items of the batch are still written), 2 for a usage error (no REF and no `--all`, both, `reject` without `--reason`), 3 when the revisions are written but the commit failed (takes precedence over 1). `approve`/`reject` do not rebuild the db: run `knowledge.py build` afterwards (a note says so), and until then `review-pending` still lists the fact. **Default status filter**: `search`, `facts` and `subjects` show only `active` facts by default (superseded and retracted facts are hidden too, the same rule `modes.py` uses); `--include-pending` adds pending ones; `--status X` (on `search` and `facts`) shows only status X and wins over `--include-pending`; `subjects` counts active facts (0 for a subject with none, it is still listed). `show <id>` and `show --as-of` by explicit id, and `history`, work for any status (a pending fact's header says `status=pending`); the library `get_fact` is deliberately unfiltered. The library functions take `include_pending=False` (and `status=` where listed); `modes.py` private mode still shows every status.
- **Supersede / retract (#8, `lifecycle.py`, `cli_lifecycle.py`)**: lifecycle active -> `superseded` / `retracted`, always recorded as a revision (#30), never as an edit to the original entry. `knowledge.py supersede REF --by REF --reason "..."` appends `status: superseded` with `superseded_by` = the replacement's `source_key`; `knowledge.py retract REF --reason "..."` appends `status: retracted` (and clears `superseded_by`). `REF` is a fact id (needs the built db) or a `source_key`, so facts from `general_facts.json`, `pilot_facts.json` and `facts_batch*.json` all work (an entry with no stored key has a derived `legacy-...` key, shown by `history`). `--reason` is required. A rebuild puts the new status in `facts` (and resolves `superseded_by` to `superseded_by_fact_id`); `history` shows the revision with its reason; `show --as-of` a date before the change still shows the old status; `audit-claims` flags any claim citing the fact. Rules: only an active fact can be superseded (a pending one is approved/rejected first; a retracted one needs an `active` revision first), never by itself, by an unknown / retracted / pending fact, or in a cycle (A -> B -> A, or a longer loop); superseding by the same replacement again, or retracting an already retracted fact, is a clean "no change" (exit 0, no revision, no tree check, no commit). The precondition is re-checked under the revision log's lock, so concurrent calls write one revision. Exit codes like `approve`: errors and refusals 1, a written-but-uncommitted revision 3; same commit rules as `add-fact` (clean tree required unless `--allow-dirty`, one commit of `fact_revisions.jsonl` only). **Reversal** has no command: it is another revision back to active, appended through the library with a reason, e.g. `revisions.append_revision(key, {"status": "active", "superseded_by": None}, "restored because ...", "cli")` (history keeps every step; nothing is deleted). Library: `lifecycle.supersede(ref, by_ref, reason, ...)` / `lifecycle.retract(ref, reason, ...)` return a `LifecycleResult` (`ok`, `outcome`, `reason`, `revision`, `commit`, `commit_error`); callers must check `.ok` (a test scans for discarded results). Not covered: detecting which facts should be superseded.
- **Set visibility (#23, `lifecycle.set_visibility`, `knowledge.py set-visibility REF normal|private --reason "..."`)**: promote or demote a fact by appending a revision with the new `visibility`; the original entry is never edited, `history` shows the revision with its reason, and a rebuild is needed for it to take effect (then a promoted fact appears in `knowledge-normal.db` and a demoted one is gone). Raising to `private` always works. Lowering to `normal` is checked first with the privacy resolver (`privacy.check`, the same subject tree and known-subject context as `privacy check`: subject tag, ancestor tag, keyword/name rule, unknown subject, evaluated on the fact's current, possibly revised, statement) and is **refused with the resolver's explanation** when the floor says private, because the build re-applies the floor raise-only and a `normal` revision would be a silent no-op that misleads `history`. Lowering needs the built db for the subject tree (fail closed: refused without one; run `build` first), and a rules file that cannot be read also refuses. Asking for the visibility the fact already has is a clean "no change" (exit 0, no revision, no tree check, no commit). Pending and retracted facts can change visibility too. Exit codes and commit rules are the same as `supersede`/`retract`. Note on `show --as-of`: the build raises every revision of a currently-private fact to private (history is never more visible than the fact), so after a **demotion** the db shows the earlier revisions as private too (the log line keeps the earlier `normal`); after a **promotion**, `--as-of` before it shows `private` and after it `normal`. Not covered: bulk promotion from `is_personal`.
- **Provenance**: optional `captured_via` (`cli`, `mcp`, `migrate-memory`, ...), `session_id`, `captured_at` (stamped from `clock.py`) and `source_quote` on `facts`. `add_fact.py` (`--captured-via`, `--session-id`, `--source-quote`) requires `session_id` and `source_quote` when `captured_via` is `mcp`; a quote may then stand without a `--source-citekey`. Plain CLI adds need none of it. `knowledge.py show` prints them (and the visibility and source key) when set.
- **Claims and the stale-premise audit (#1)**: `claims` has a nullable `inference_type` (`deductive`, `inductive`, `abductive`), set on new claims only; the 2 existing claims are deliberately not backfilled (NULL = unclassified). A claim's premises are its `claim_facts`. `claims_audit.audit_claims(db, today=None)` lists every (claim, premise) where the fact is `superseded`, `retracted`, or still active but past an ISO-date `recheck_by` (`reason` = `superseded` / `retracted` / `past_recheck_by`); `v_claims_with_stale_premises` is the SQL view for the status cases. `recheck_by` text that is not an ISO date is never flagged; `unparseable_rechecks(db)` lists it. The `knowledge.py audit-claims [--json]` command is not wired yet (it waits for the Typer migration, #34); until then call `claims_audit.audit_claims` directly. `supersede` / `retract` (#8) are what put facts into the first two states.
- **Auto-commit of knowledge-private (git as backup and safety net)**: `add_fact.py` commits its change to `knowledge-private` itself (message `add-fact: <subject> (<trust_level>)`), so every mutation is already in git history and the tree is clean afterward. That is what makes git a reliable backup and safety net for the private data; the primary, queryable fact history is the revision log (#30), not git. Before writing, it refuses (exit 1, nothing written) if `knowledge-private` has any uncommitted change, staged, unstaged or untracked, so a commit never bundles unrelated edits; `--allow-dirty` skips that check for a deliberate batch edit (the commit still contains only the facts file). If the commit itself fails (hook, no git identity, ignored file) the fact is in the JSON but uncommitted, the error says so, and the exit code is 3. The repo is found from the data file's directory (so `KNOWLEDGE_PRIVATE_DIR` works); a data dir outside any git repo is written without committing and a note says so. It never pushes. Future mutating commands (`approve`, `supersede`, `retract`, `set-visibility`) reuse `private_git.py`: `find_repo(dir)`, `ensure_clean_tree(repo)` before writing, `commit_private_change([path], message, repo)` after, with `PrivateGitError` for failures.
- **Schema change**: edit `schema.sql` directly (it's the definition, not a migration diff), then rebuild.
- **New external path an ingest script needs**: add it to `knowledge-private/local_paths.py`, never inline it in a script here.

## Architecture enforcement (#36)

The layering the program relies on is checked mechanically, by **tach** (`tach.toml`: per-module import allowlists and layers) and **import-linter** (contracts in `pyproject.toml`), and both run inside `uv run pytest` (`tests/test_architecture.py`). A violating import fails like a failing test.

Run them directly:

- `uv run tach check` : module boundaries (every top-level module and every numbered script is a tach module).
- `uv run python tests/arch_check.py` : tach + import-linter + the git scan, the same as the test. **Plain `uv run lint-imports` does not work here**: import-linter only analyses packages and this repo is flat modules (`'x' is a module, not a package`). `tests/arch_check.py` copies each importable top-level module into a throwaway package `kn/` (rewriting only project-internal imports, `import privacy` -> `import kn.privacy`, lazy ones included) and runs `lint-imports --config pyproject.toml` on that, so contracts name `kn.<module>`. The copy is parsed, never executed.

**Layers, top to bottom:** serving (`inbox`; `mcp_server`, planned) > CLI (`knowledge.py`, `cli_*.py`, `cli_parity.py`) > pipeline (`build.py`, numbered scripts, `backfill_*`, `clean_concerts_csv`, `export_music_taste`, `snapshot_date`, `_shared`) > libraries (`add_fact`, `revisions`, `review`, `lifecycle`, `facts_batch`, `migrate_memory`, `privacy`, `modes`, `claims_audit`, `normal_db`, `leak_test`, `private_git`, `clock`, `paths`). The pipeline sits above the libraries because the ingest scripts and `build.py` call them (`revisions`, `privacy`, `normal_db`); the direction that is forbidden is library -> pipeline.

| Rule | Why | Enforced by |
|---|---|---|
| Libraries never import the CLI, serving or pipeline | CLI/serving are thin wrappers over library functions (#34); a library importing them cannot be reused by the other callers | tach (`layer` + `depends_on`), import-linter `libraries-never-import-upward` |
| Libraries and `cli_parity` never import `typer`/`click` | `build.py`/`add_fact.py` run standalone; the parity registry stays importable without Typer. `knowledge.py` and the `cli_*.py` modules are the only Typer entry points | import-linter `typer-only-in-knowledge` |
| CLI never imports serving, with ONE exception: `cli_inbox -> inbox` | serving is the top layer. The `inbox` command has to START the server, so `cli_inbox` is a launcher: it imports `inbox` and calls `inbox.serve`, and nothing else in the CLI may. Launching in a subprocess was rejected: it would need a second exception (the `subprocess` allowlist), lose the in-process `on_ready`/Ctrl-C handling and gain nothing. The exception is exactly two things: the inline `# tach-ignore inbox` on the one `import inbox` line of `cli_inbox.py` (tach's layers cannot be overridden by `depends_on`) and the single `ignore_imports` line `kn.cli_inbox -> kn.inbox` in `cli-never-imports-serving`. Negative tests prove every other CLI module importing `inbox`/`mcp_server`, and `cli_inbox` importing `mcp_server`, the pipeline or an unlisted library, still fails; another test pins that there is exactly one `tach-ignore` in the repo | import-linter `cli-never-imports-serving` + tach layers |
| Serving never imports the pipeline | the serving layers must not be able to rebuild or ingest | import-linter `serving-never-imports-pipeline` + tach layers |
| Serving reads facts only through `modes`, writes only through `review`/`lifecycle` | `modes` enforces off/normal/private (#22). `inbox` may import `review`, `lifecycle` (and `modes`) and the standard library; importing `knowledge` queries, `claims_audit`, `add_fact`, `revisions`, `privacy`, `private_git`, `facts_batch`, `migrate_memory`, `normal_db` or raw `sqlite3` could bypass it. There is **no exception**: the inbox used to import `revisions`/`privacy`/`private_git` directly, and that logic was moved (see below). Only direct imports are checked | import-linter `serving-reads-facts-through-modes`, tach allowlist |
| `paths` is imported only by an allowlist | it is the only module that knows personal paths | tach `depends_on` (only `add_fact`, `build`, `knowledge`, `migrate_memory`, `privacy`, `revisions`, `clean_concerts_csv`, `export_music_taste` and the ingest scripts list it) |
| `private_git` is the only module running git against knowledge-private | its lock, clean-tree and detached-HEAD checks must not be bypassed (#10) | tach (only `add_fact`, `review`, `lifecycle`, `facts_batch`, `migrate_memory`, `knowledge` list it), import-linter `subprocess-allowlist` (only `private_git` and `knowledge` import `subprocess`), and an AST scan in the test for `"git"` command lists / `os.system` elsewhere |
| No cycles among libraries, fixed order | a layers contract forbids any upward import, hence cycles | import-linter `libraries-layered` (one documented lazy exception: `leak_test.self_test` imports `normal_db`, which lazily imports `leak_test`) |

tach settings that matter: `layers_explicit_depends_on = true` (otherwise a higher layer may import any lower layer without declaring it, switching the allowlists off), `root_module = "forbid"` (an unlisted `.py` that imports anything is an error), `exact = true` (an unused `depends_on` entry is an error), `ignore_type_checking_imports = false`. Lazy imports inside functions are checked by both tools.

**Adding a module:** pick its layer. (1) `tach.toml`: add a `[[modules]]` block with `layer` and the exact `depends_on`; add it to `knowledge`'s `depends_on` if it is a `cli_*` module; add it to any allowlist that should list it (`paths`, `private_git` importers). (2) `pyproject.toml`: a library goes in the `source_modules` of `libraries-never-import-upward` and `typer-only-in-knowledge` and on a row of `libraries-layered` (a new row, or `|` beside an independent sibling); a CLI/pipeline module goes in the `forbidden_modules` of `libraries-never-import-upward`; a serving module goes in the serving contracts. `tests/test_architecture.py` fails if the configs disagree about what exists. A new numbered script: add it to `NUMBERED_SCRIPTS_EXCLUDED` in `tests/arch_check.py` and as a pipeline module in `tach.toml` (it is not importable, so only tach sees it).

**Planned modules.** Only `mcp_server` (#2) is still planned: its entries in both configs are on lines starting `#planned:`. When its file lands, delete the `#planned: ` prefix on its lines and set its `depends_on`/layer row to what it really imports; the test names the exact lines if you forget. The negative tests enable every planned line, so the planned layout itself is exercised. (The wave-4 modules `lifecycle`, `facts_batch`, `migrate_memory`, `cli_lifecycle`, `cli_migrate`, `cli_facts_batch`, `cli_inbox` and `inbox` are active with their real import graph.)

**Where the inbox's logic lives (#36).** `inbox.py` is serving, so it holds no write logic, no privacy rules and no git. `lifecycle.edit_fact` (the `edit` command and the edit form) and `lifecycle.set_visibility(..., expect_status="pending", raise_only=True)` (the "Make private" button; `set-visibility` itself is unchanged) do the writes; `review.pending_view` / `review.visibility_basis` give the page its pending overlay and the rule behind each visibility; `review.resolve_ref` is the public ref resolver (it was `review._resolve`). The exception inventory is therefore: `cli_inbox -> inbox` (above), `private_git -> subprocess` and `knowledge -> subprocess`, and `leak_test -> normal_db` (lazy cycle); `tests/test_architecture.py` pins that list.

**What these tools cannot catch** (the regex scan tests in `tests/test_modes.py`, `test_privacy.py`, etc. remain the backstop): SQL read through a string (`SELECT ... FROM facts` in any module), dynamic imports (`importlib`/`__import__`/`exec`; `build.py` loads the numbered scripts this way), what a permitted `subprocess` user runs (the AST scan only catches literal `"git"`), a module reading the db file without importing a forbidden module, and anything about which functions of an allowed module are called (no tach `interfaces` are declared; e.g. `revisions` imports `add_fact`'s underscore helpers). The numbered scripts are invisible to import-linter and checked only by tach.

## Known caveats

- `sqlite3` (the CLI) on this machine is not compiled with FTS5. Full-text search (`facts_fts`, `sources_fts`) works from Python's `sqlite3` module — use `python3 knowledge.py search "..."` — or a client like DB Browser for SQLite / Datasette, but not from the bare `sqlite3` command line.
- `measurements` from the raw vault logs (44K+ rows) are a snapshot as of the last rebuild, not a live-synced view — the vault's own db keeps growing as you log new sets/meals, this doesn't.
- `is_personal` is a heuristic classification (pronoun/fingerprint/file-origin signals), not hand-verified per fact — see `classify_is_personal()` in `04_ingest_facts.py`. **It is not a privacy boundary**: the facts it marks not-personal include sensitive material (health, for one). Use `facts.visibility` for anything about who may see a fact.
- `facts.visibility` is `private` or `normal` (`schema.sql` CHECK, indexed). Every fact is `private` unless its JSON entry says `"visibility": "normal"`; it is never derived from `is_personal`. `add_fact.py --visibility normal` sets it (default `private`, invalid values are rejected). Nothing filters on it yet.
- **Privacy rules (#31, `privacy.py`)**: the stored `visibility` is computed, never chosen by the model: the most restrictive of (1) what the caller asked for, (2) the `private` tag on the fact's subject or any ancestor (subjects form a tree via `parent_id`), and (3) a keyword/name list matched on whole words, case-insensitively (`brother` does not match `brotherhood`; punctuation and hyphens are boundaries; rules are literal text, never regexes). A caller can only raise visibility. A subject that does not exist yet is `private` (fail closed) whenever the subject list is known. The result explains itself (`Resolution.explain()` names the rule). **This is word matching plus subject tags, not semantic detection**: nicknames, pronouns and unlisted names are missed, which is why human review stays. Rules live in `privacy_rules.json` in `PRIVATE_DATA_DIR` (knowledge-private; it holds names, so it is never in this repo), format `{"version": 1, "subject_tags": {"family": "private", "new-topic": "normal"}, "keywords": ["..."]}` (a `normal` tag just registers a subject as known; it never lowers). **No rules file means empty rules** (no tags, no keywords); a corrupt or non-object file is an error that fails the build and refuses `add_fact`. `add_fact.append_fact` stores the resolved value (and returns `AddResult.privacy`); steps 04 and 11 re-apply the current rules to every fact at the end (`privacy.apply_rules_to_db`, raise-only, also sets `subjects.private`), so adding a rule privatizes old facts on rebuild, while removing a rule never downgrades a fact stored `private`. Tag inheritance needs `parent_id`, which step 06 sets, so step 11 (last) is the pass that sees the whole tree. CLI: `knowledge.py privacy check "<statement>" --subject s` prints the resolved visibility and which rule raised it (it uses the subject tree from the live db, read-only, plus subjects already in `general_facts.json`; with no db it uses empty context, so the unknown-subject rule cannot fire); `privacy rules` shows what is loaded; `privacy tag|untag|add-keyword|remove-keyword` are the only supported way to edit the rules file: like `add-fact` they refuse a dirty knowledge-private tree (`--allow-dirty` to override), commit only the rules file (exit 3 if the file is written but the commit fails), support `--dry-run`, create the file on first use, and an edit that changes nothing writes and commits nothing. `add_fact.py` prints a stderr note naming the rule when the stored visibility is stricter than requested. The library functions are `check`, `tag_subject`, `untag_subject`, `add_keyword`, `remove_keyword`, `load_rules`, `save_rules`.
- **Batch `add_facts` and the `register facts` protocol (#32, `facts_batch.py`, `cli_facts_batch.py`, `docs/register-facts-protocol.md`)**: `facts_batch.add_facts(items, status='active', captured_via='register-facts', session_id=None, data_dir=None, dry_run=False, commit=True, allow_dirty=False, session=None)` validates every item with `add_fact.validate_fact`, resolves visibility with the #31 resolver (the requested `visibility` is only an input; the stored value is the most restrictive, and the result names the rule), assigns a `source_key` and provenance, then appends the whole batch in ONE lock and ONE atomic write (`add_fact.append_records`, which serialises with `add_fact`) and ONE `private_git` commit (`add-facts: N fact(s) (subjects)`; same semantics as `add-fact`: dirty tree refused unless `allow_dirty`, non-repo dir written with a note, commit failure leaves the facts written and sets `commit_error`, CLI exit 3). **Atomicity**: validation is all-or-nothing (any invalid item, an unknown key or a caller-set `source_key`/`status`/provenance field: nothing is written, every item gets an outcome `invalid` or `not_saved`, resend the whole list); everything after validation is per item: a privacy raise is saved private and reported, an exact duplicate (same subject and statement, ignoring Unicode form, whitespace runs and case, against the whole facts file or earlier in the batch) is skipped as `duplicate` so re-running a file writes nothing, and with a `modes.Session` a private result in normal mode is `refused` (mode off refuses the call). Items need `statement`, `subject` and freshness (#7: `recheck_by`, or `no_decay: true` with `recheck_rationale`); `trust_level` defaults to `unverified`; statements and dates are stored exactly as given, never resolved. Max 1,000 items per call. Facts reviewed in the chat are `active`; `status='pending'` queues them for #6 review. Visibility resolution sees the facts file as it was before the batch, so a brand-new subject is private for every item that uses it. Duplicate detection does not know about facts only in other data files, and a previously retracted fact still blocks an identical re-add. CLI: `knowledge.py add-facts [FILE|-]` reads the JSON list (what the MCP tool will receive); `--dry-run` prints each item's resulting visibility and the rule behind it and writes nothing; exit 1 on any error or non-saved item (duplicates are fine), 3 on commit failure. Callers must read the `BatchResult` (an AST test fails on a discarded call). The MCP tool itself waits for #2; the protocol text and its under-2,048-character instruction block (for #27) are in `docs/register-facts-protocol.md`.
- **Normal-only DB (#21, `normal_db.py`, `leak_test.py`)**: every `build.py` run, after the atomic swap of `knowledge.db`, also writes `knowledge-normal.db` next to it (same temp-file + `os.replace` way) so a remote-served connector never holds anything private. It is built by copying a whitelist INTO a fresh empty db (never by deleting from a copy, which leaves pages and FTS shadow rows behind). In: `facts` with `visibility='normal'` on a non-private subject chain that also still passes the current privacy rules (re-resolved at build time, so a rule added since ingest keeps a fact out); `fact_revisions` of those facts that are themselves normal (an older private revision is dropped; a fact now private has no history); `fact_sources` rows of those facts, `quote` and `locator` included because they belong to a normal fact (a private fact's quote on the same source is not copied); only the `sources`/`authors`/`source_authors`/`publishers` they cite; their `subjects` plus ancestors; rebuilt FTS; and a `v_subjects` view that counts normal facts only and lists only subjects having one. Left out columns: `is_personal`, `notes`, `origin_file_id`, `provided_by`, capture/session fields, `source_quote` on facts; `origin_path`/`created_at` on sources; `session_id`/`change_reason`/`notes` on revisions. Absent tables (not empty): claims and their links, `vault_files`, and every non-fact table. `superseded_by` links to a fact that is not in are nulled. After building, `leak_test.scan_against_full` derives markers from everything private in the full db (non-normal facts, their notes/quotes/citations, claims, vault paths, source origin paths, private subject names, private revisions) and greps both every cell and the raw file bytes of the normal db; any hit fails the build. If the normal build fails, `build.py` exits non-zero, keeps the main build, and removes any previous `knowledge-normal.db` (a stale one could still hold a fact since made private). `python3 leak_test.py` runs the fixture self-test (known markers; also proves the scan fails when a marker is injected); `python3 leak_test.py --full F --normal N` checks a real pair. Not covered: private data that is in a normal fact's own statement, a cited source's name/description, or a normal quote and that no rule catches (same word-matching limits as the privacy resolver).
